# Offline expectation-review comparison

`diagnostics.expectation_review_checkpoint` freezes matched requests at an explicit
recorded post-probe turn. It is preparation only: no provider, Docker, evaluator,
candidate restoration or live collector. The packet must not be used with ordinary
resume or earlier continuation collectors.

Control is the exact selected recorded request. Treatment adds only
`state.expectation_review` with fixed generic wording about expected-value provenance,
rejecting alternatives and independent public requirements on the same input.
No task-specific formula, counterexample or operator outcome is supplied. Tools,
history, plans, notes, completion policy and budget remain identical between arms.
Stored budget values describe the old boundary and authorize no new spending.

Source journal/envelope/public-task hashes and runtime are verified. The selected
input is verified against canonical public context; the prefix stops before its
count, excluding selected generation/action and later outcomes. Both input artifacts,
cue, cutoff and hashes are journal-bound in an external output root. Validation
reconstructs the pair; existing artifacts and source bytes are never edited.

The concrete development comparison inherits advice removal in both arms. Therefore
it tests adding a review at this decision, not a fresh solve or the ordinary baseline.
Any future execution needs a separate restoration design, canonical context binding,
first-delivery/recount checks and authorization. This module does not guarantee
multi-mutation restoration or native continuation equivalence.

Measure whether the agent challenges the disputed expectation against independent
evidence on the same input, revises its hypothesis appropriately, and verifies its
final candidate. More prose or probes alone are not improvement; efficacy is NOT_RUN
until executed, and a single development pair cannot establish generality.
