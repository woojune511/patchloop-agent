# Repair after an acquired original failure

`diagnostics/post_reproduction_repair.py` prepares one explicitly funded
continuation after a completed original-reproduction tool batch. It does not
change ordinary resume admission, agent defaults or repair policy.

The source must be a hash-bound dev-train OpenAI segmented run with unchanged
base, one acquired/refuted original case, settled model/tool/probe receipts and
positive remaining resources. `after_tool_batch=True` includes the completed
batch itself. It derives counters, elapsed time and settled cost from receipts,
not an older prepared request. The public authored program, case, action/input
identities and old JSONL bytes remain fixed. Nested fork CAS references are
resolved through the parent's verified hash/size/media-type mapping.

Preparation uses a fresh external branch and a finite scripted stop. The normal
runner builds the first repair request through its existing public segment
handoff. The audit compares the latest action/input identity and the complete
reproduction object, including desired/failure comparisons and captured calls,
against the saved result. Historical encrypted reasoning is excluded; no target
execution or provider/credential access is needed. The actual repair stage and
available tools are derived normally, not prescribed by the diagnostic.

The sealed manifest binds source/runtime/diagnostic hashes, model, credential
path, one repeat, new positive cap, inherited resources and first public request.
Only elapsed-time fields, transport timeout and the derived segment ID are
normalized for preparation-to-dispatch comparison. Resource admission decisions,
cost forecasts, evidence and tool schemas stay bound. Input counting immediately
before dispatch compares the unnormalized actual payload. SDK retries remain zero.

Collection requires the exact manifest hash and new cap. It reuses the ordinary
runner for edits, original replay, public regressions, bounded revisions, finish
and isolated evaluation. The previous first-probe diagnostic stop is absent.
Current execution commit and historical/current probe receipts are recorded
separately. No private evaluator information is projected into model requests.
No image is pulled or built, and Docker Desktop is not started automatically.

Historical funds remain closed. The new invocation ledger accounts only new
usage, while the branch ledger preserves prior usage. Original remaining
response/action/edit/time allowances are not reset. Result roots are single-use;
count, transport, billing, execution and cleanup uncertainty stop the allocation
without automatic resume. Report recorded settled usage separately if total
billing is unknown.

Success criteria must inspect unchanged-call error absence and processing,
public regressions, normal submission and isolated acceptance separately.
The current null diagnostic-rules case also needs an independent post-run check
of captured outputs versus the authored verdict. Neither offline input delivery
nor a repaired checkpoint establishes a clean-start solve or general improvement.
