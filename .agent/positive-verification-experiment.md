## Problem and causal question

The SQLFluff final-verification audit found that the saved symptom-only predicate
accepted a wrong result. Replaying that program would not establish correct repair.
The later public-predicate response encoded the expected example correctly under
static inspection, but quotation rejection prevented execution. That result is
NOT_ASSESSABLE under its closed report contract, not demonstrated inability to
write a useful check. These are the specific reasons to investigate positive
expected behavior rather than adding another broad planning or replay rule.

Does explicit guidance to assert the required positive result produce a useful
discrimination that changes a repair decision and improves final correctness?
Alternatives: the model can author the check but does not select it; construction
or invocation is wrong; observations are correct but the repair is not; the same
repair is already found by baseline. More probes alone would not support the claim.

## Outcome and decision criteria

Primary evidence per row is the registered isolated task acceptance, current-diff
public regression, sandbox safety, exact submitted patch, cost and elapsed time.
Freeze a separate public-example assessment before dispatch: full expected output
for 1733, and no L031 violations for both explicit TSQL examples in 1625. Calibrate
these against the unchanged base through the prepared public probe environment;
both must expose their public defect. After the entire batch, run the same programs
on hash-verified submitted workspaces. A public-example PASS covers only those
examples; retain original isolated acceptance separately. Bind programs, base
receipts and the operator driver to the packet. Never expose them to the solver.
Review public probes to determine whether an independent expected result was
actually checked, whether a wrong candidate was exposed, and whether that result
changed a repair. Quote validity, normal exit and probe counts are separate axes.
Do not feed operator controls, previous patches or grading results to the solver.

Consider provisional use on this exposed scope only if B resolves more tasks in
both repetitions, loses no A-successful task in either repetition, and shows an
executed discriminating observation followed by a correct repair. An increase in
aggregate cost or time above 25% requires an explicit tradeoff decision rather
than automatic adoption. Eight runs cannot establish general superiority.

Tied or mixed correctness, non-exercised mechanism, infrastructure/resource censoring
or more checks without a better repair preserves baseline. No further prompt
variant follows automatically. Choose a later execution-path or preservation
intervention only if new public traces identify that specific remaining failure.
