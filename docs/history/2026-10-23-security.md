# Python and container security maintenance

Date: 2026-10-23. Operator security maintenance; official=false. No provider call
or benchmark repair experiment ran. Existing evaluator images were inspected in
read-only, network-disabled metadata containers; no benchmark test or acceptance
command ran. The mock smoke reached its local isolated evaluator.

## Problem and scope

The user requested a check of the reported certifi incident and necessary Docker
updates. The immediate risk was TLS trust: compromised eMudhra intermediate keys
required removing `emSign ECC Root CA - G3`. The internet-facing host installer and
HTTP client were exposed even though the repair containers normally have no network.
Updating one certifi installation cannot update independent OS, pip, ensurepip,
Conda or Node trust stores.

Sources: [Python incident guidance](https://discuss.python.org/t/information-for-python-users-regarding-emudhra-emsign-ca-certificate-security-incident/109576),
[uv 0.13.5](https://github.com/astral-sh/uv/releases/tag/0.13.5),
[Debian DSA-6572-1](https://lists.debian.org/debian-security-announce/2026/msg00487.html).

## Observed evidence

- Docker Desktop 4.92.0, Engine 29.8.0, no containers at the initial inventory.
  This is environment evidence, not a full host-security certification.
- There were 93 local images. All 91 Python images had the affected root in at
  least one inspected trust bundle. Node 24.18.1 also retained it. The remaining
  hello-world image has no shell/Python and was not a Python trust-store target.
  Inventories covered OS bundles, installed certifi, vendored pip and ensurepip
  wheels; they are not a proof that every possible embedded store was discovered.
- The initial batch covered 90 Python images. The Python 3.6 task image needed a
  compatible inspection path; its later inventory confirmed affected bundles.
  Some old Conda PEM files had non-ASCII comments and were not parsed by the simple
  inspector. Other stores in those same images already confirmed exposure.
- Host certifi was 2026.7.22, uv 0.11.16 and project-managed Python 3.14.5. The
  project venv had no pip, but the managed base interpreter had its own pip/ensurepip.
- Even the freshly pulled official Python 3.12.15 image had pip 25.0.1 and the
  affected ensurepip wheel. Its OS CA package was already 20250419+deb13u1.
  Thus merely pulling a fresh official tag did not resolve all stores.
- Project dependency audit also reported CVE-2025-71176 in pytest 8.4.2. The two
  reported entries were duplicates of one advisory, not two independent flaws.
  [pytest's changelog](https://docs.pytest.org/en/stable/changelog.html#pytest-9-0-3-2026-04-07)
  records the temporary-directory fix in 9.0.3.

## Changes and decisions

- Require certifi >=2026.10.19 and pytest >=9.0.3,<10; lock 2026.10.19 and 9.1.1.
  Other project package versions remain fixed. Require uv >=0.13.5; CI pins 0.13.5.
- Updated host uv to 0.13.5 using the native Windows certificate store for
  bootstrap; upgraded the project-managed Python 3.14 to 3.14.9. Locked sync
  recreated the venv for that patch version. Managed pip/ensurepip are 26.2.2.
- Built a public-only Python 3.12.15 image from an exact official digest, refreshed
  available OS packages without build cache, and installed the official checksum-pinned
  pip 26.2.2 wheel in both site-packages and ensurepip. Added the recipe; rebuilt the
  graphics image from that base. No task data, credentials or evaluator packages
  entered these images. Active runtime pins select the reviewed output digests.
- Default probe identity now derives from the runtime registry, removing a second
  independent copy of the default digest. Existing isolation and tool policies remain.
- A non-root check caught the remote ADD default mode 0600 on the ensurepip wheel;
  the final recipe specifies 0644. A venv check that copied Python into noexec tmpfs
  was correctly denied; using the normal symlink-based Linux venv verified pip
  bootstrapping without weakening the tmpfs restriction.
- Historical task/evaluator images and Python 3.9/3.10 profiles retain their bytes.
  Their unsupported interpreters and old dependencies are restricted to the existing
  offline, read-only execution boundary. Do not reuse them as general networked
  environments. Updating task dependencies indiscriminately would change benchmark
  conditions without proving security or task compatibility.

## Broader scan and limits

Docker Scout required a login, so it produced no vulnerability result. A separately
downloaded Grype 0.121.0 executable was checked against the official release SHA256;
its local scan used the 2026-10-23 vulnerability database. No image was uploaded.

The final base produced 208 package/advisory matches (99 distinct IDs),
including two Critical matches from generic OpenSSL 3.5.7 detection. Installed
Debian openssl/libssl3t64 are 3.5.7-1~deb13u3: both Critical entries are already
backported according to Debian's tracker, which takes precedence over a bare
upstream version match: [CVE-2026-63073](https://security-tracker.debian.org/tracker/CVE-2026-63073),
[CVE-2026-75803](https://security-tracker.debian.org/tracker/CVE-2026-75803).
The gzip warning similarly needs the Debian revision:
[CVE-2026-41992](https://security-tracker.debian.org/tracker/CVE-2026-41992)
is fixed in the installed 1.13-1+deb13u1.

The final graphics image produced 263 matches (132 distinct IDs). Its additional
Critical entry is [libxml2 CVE-2026-6653](https://security-tracker.debian.org/tracker/CVE-2026-6653),
still present in Debian trixie and classified there as a minor issue with no DSA.
This is a real residual finding, not an OpenSSL-style backport false positive.
No fixed trixie package was available. Keep this optional public graphics runtime
inside the existing offline sandbox; switching to unstable distribution libraries
or building an unreviewed libxml2 was not justified by this maintenance. A future
use requiring untrusted XML parsing outside that boundary needs a supported fix
or separately verified replacement image first.

Other matches remain, including Debian entries marked wont-fix/not-fixed and
[zlib CVE-2026-85091](https://security-tracker.debian.org/tracker/CVE-2026-85091),
whose tracker status and upstream affected-range note need reconciliation. No
available Debian upgrade resolved every match. The scan is triage, not evidence of
exploitability or an all-CVE clean bill. Network denial, non-root probes, read-only
mounts and process limits reduce exposure but do not eliminate interpreter/library
or container-escape risk. Do not weaken these controls to run legacy workloads.
