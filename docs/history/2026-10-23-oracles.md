# Separate failure oracles and fund one response correction

Date: 2026-10-23. Implementation and offline validation only; official=false.

## Question and decision

The [closed live pilot](2026-10-23-repro-live.md) executed the original caller but
encoded its F0010 failure as the desired result. An incomplete response later spent
the current allowance without a tool action, leaving two minimum calls for a path
that needed three. These expose independent gaps: ambiguous oracle meaning and a
recovery slot without correction money. More output or another model might still
fail; neither observation establishes the cause of unsuccessful LLM repair.

Fresh original probes now bind separate reported-failure and desired-result values.
Opt-in `completion-recovery-v1` funds one response correction at the requested output
ceiling. Existing cost policies/defaults remain unchanged. No allocation is reopened.

## Implementation

- Fresh original purposes require bounded strict `reported_failure_json` and desired
  `expected_json`, with different canonical values and separate comparisons. A healthy
  unchanged-base root acquires failure only with failure match and desired mismatch.
  A third value is `not_reproduced`; desired mismatch still blocks finish.
- Known preflight rejections remain in request/error accounting but create no
  completion case. Accepted uncertain and legacy unknown requests remain unverified.
  Legacy bindings and admitted pending purposes retain their bytes/rules. Restart
  alone cannot give a newly rejected request the legacy exception.
- `completion-recovery-v1` reserves successful minimum successors plus one correction:
  60K uncached input + invocation output ceiling, normally 25K. It retains one model
  slot and no extra tool slot. The first durable protocol correction consumes the
  run-wide credit; valid batches/restart never renew it. That correction requires the
  full output allowance. Consecutive correction limits, settlement and uncertainty
  stops remain unchanged.

Both oracles and the issue-to-caller mapping remain model-authored. First-root
observation selection is unchanged; later base observations cannot automatically
promote that root. A funded correction may still produce no action. Other successors
retain only 128-token minimum admission; tool-failure recovery has no new credit.

## Fixed-cap admission comparison

Both arms use virtual USD 0.40, the same scripted CSV repair, 60K uncached input for
every request and full consumption of each admitted output ceiling. The second
response is settled but incomplete with no action; the following response is the
correction. Mini pricing gives minimum unit USD 0.045576 and correction unit
USD 0.157500 at 25K output. No prices or model calls were fetched in this local test.

| Policy | Output ceilings across five dispatches | Virtual cost | Scripted outcome |
| --- | --- | ---: | --- |
| completion-minimum-v1 | 25000, 13504, 128, 128, 128 | 0.399996 | check PASS, submitted |
| completion-recovery-v1 | 3376, 128, 25000, 128, 128 | 0.354420 | check PASS, submitted |

This supports the reservation/correction mechanism and shows its tradeoff: ordinary
responses get less output before the first error. It does not show a repair advantage;
both arms follow scripted actions even with 128 output tokens. Their synthetic
provider/sandbox identity intentionally ends at evaluator ERROR after submission;
only the separate standard mock smoke reaches isolated acceptance PASS. A second
consecutive incomplete response stops after three dispatches and one correction.
Known interruption restores the credit/charges once; unknown count/dispatch is not
retried. No result assumes that unspent cap or a funded output allowance means progress.

## Scope and next question

No paid solve, Docker execution, Linux CI, generalization or causal repair improvement
is established here. All prior allocations remain closed. A future comparison needs
its own exact task/model/cap and evidence-based reason, with oracle correctness and
correction usefulness judged separately.
