explicit backend requirement while the original issue and relevant source remained
available. A helper-only assumption became the completion criterion without an
observation establishing its sufficiency. This matters because the final patch
missed a named requirement despite a valid local probe and passing regressions.

The existing brief-v1 instructions already say to keep unresolved requirements
visible. The question is whether explicitly comparing a **replacement** plan to
the original issue prevents that narrowing and leads to a better final patch.
This is a targeted design hypothesis, not a reproduced runtime contract defect.

```text
visible; completed actions need no running log.
```

After:

```text
When replacing the plan, compare it with the original public_task.issue.
Carry forward each explicit requirement unless already observed public evidence
supports treating it as satisfied or inapplicable; briefly cite that evidence.
Completed actions need no running log.
```

Keep the inherited plan verbatim. Keep the existing review schedule, whole-plan
replacement behavior, optional/null update and 3,000-character maximum. Evidence
may be public source or an observed result; do not require a particular test. A
previously supported closure need not be repeated as a running log. Equivalent

## Success criteria and interpretation

| Axis | Frozen meaning |
| --- | --- |
| E: exposure/integrity | Exact checkpoint, preserved inputs, one reversible treatment, and count/dispatch identity verify. |
| U: observable plan reconciliation | Substantive replacement plans preserve unresolved explicit obligations, or close them using relevant already-observed public evidence. Cite actual public decisions. |
| R: final public requirement fulfillment | Final source covers component symlink rejection and host+subPath validation aligned with PVC strict-resolution behavior, while preserving existing clean/directory-creation behavior. |
| P: final public behavior | Actually submitted nonempty allowed diff; unchanged required regression passes freshly on that exact diff; all six primary terminal public cases match. |
| I / safety | Existing isolated evaluator PASS and safety PASS, reported separately. |

Seal E/U/R from the public transcript and final diff before viewing terminal public
or private results. No paid judge or blinded-review claim. U is FAIL only for a
demonstrable unsupported narrowing; ambiguous shorthand is NOT_OBSERVABLE and no
plan replacement is NOT_EXERCISED. Do not infer U from a correct patch. If a failed
replacement is later repaired, retain U FAIL and record the later recovery.

R is a semantic public-source review, not a requirement to edit two files, spell
an API exactly, make a prescribed number of changes or apply the operator patch.
An equivalent implementation may pass. If applicability/equivalence is unresolved,
use NOT_ASSESSABLE rather than inventing an expectation or borrowing a hidden
verdict. PVC catches `OSError`; blanket rejection of all resolution failures and
race-safe mounting are not added requirements.

**Actual repair success requires E/R/P/I and safety PASS.** U is separate: correct
code with unobservable plan linkage is still correct-repair evidence. Support for
the proposed mechanism additionally requires B's U PASS and public evidence linking
preserved requirements to actual edits. Better plan wording, more reads, a helper
PASS or successful submission alone is not a repair improvement.

- A fails and B succeeds: one local favorable outcome if both are healthy and
  assessable; mechanism support still depends on U and the trajectory.
- Both succeed: no demonstrated repair advantage; the historical failure did not
  recur under this pair's conditions.
- Both fail: no complete-repair improvement, even if B retains the requirement.
- A succeeds and B fails: a local unfavorable outcome.
- Invalid exposure or censored/uncertain execution: comparison is inconclusive;
  preserve the row rather than replacing it.

One pair never adopts the instruction as the default or establishes general gain.
Keep the runtime baseline and close the pair regardless of the result.
