모델의 선택과 런타임의 실행

Runner가 공개 상태와 허용 도구를 구성하고, 모델이 다음 행동을 선택합니다. Gateway는 요청을 검증하고 소스 수정·검사 결과를 기록합니다.

제출 자격, 원래 문제의 해결 근거, 독립 acceptance는 서로 다릅니다.
runner.py · tools.py

화살표는 주요 실행 흐름을 나타냅니다. 컨텍스트·복구·자원 관리는 별도 에이전트가 아니라 루프 전반에 적용되는 런타임 기능입니다.

무엇을 제품으로 보는가

문제를 이해하고 올바른 코드를 제출하는 에이전트. 도구 사용 횟수나 노트 생성 자체는 목표가 아닙니다.

누가 무엇을 결정하는가

모델은 공개 도구로 행동을 제안합니다. 런타임이 계약을 검증하고 실제 부작용과 증거를 기록합니다.

성공은 어떻게 판단하는가

제출, 공개 검사, 과제 수용, 격리 안전성을 따로 봅니다. 제출 가능 상태만으로 정답이 보장되지는 않습니다.

02 /

한 번의 실행을 따라가기

일반적인 실행을 여섯 단계로 풀어 썼습니다. 탐색·수정·검사는 필요에 따라 반복됩니다. 이 단계들은 이해를 위한 구분이며 강제 계획 단계가 아닙니다.

별도 명령 repair-verify — 모델 호출 없이, 제출된 추가 pytest 케이스를 그대로 기준 코드와 수정 코드에 실행하여 비교합니다. 공개 검사도 기록하지만, 테스트 기대값이 요구사항과 맞는지 또는 패치가 수용 가능한지 판정하지는 않습니다. 지원하지 않는 분리는 UNSUPPORTED로 남습니다. 명령과 요청 형식
함수 호출과 데이터 흐름을 한 번에 보기
cli.dev() → DevRunRequest → run_dev() → _run_invocation() → _run_one() → _run_one_active()
repair → RepairRunRequest → run_repair() → 같은 _run_invocation()
  1. 입력 검증과 envelope 고정

    과제·모델·정책·예산·소스 식별자를 고정합니다. dev는 운영용 과제 패키지를 로드하지만 모델에게는 공개 필드만 전달합니다.

  2. 별도 작업공간 준비

    WorkspaceManager가 기준 revision에서 작업공간을 만듭니다. 원본 저장소와 실행 상태는 분리됩니다.

  3. 현재 snapshot과 허용 도구 계산

    diff, 검사, 관찰 소스, 남은 자원을 읽습니다. 고정된 단계표를 순서대로 통과하는 대신 매 턴 가능한 행동을 다시 계산합니다.

  4. 공개 문맥 구성과 모델 호출

    공개 과제·현재 후보·최신 관찰을 제공합니다. 유료 요청은 입력 count와 비용 admission을 통과한 뒤 dispatch합니다.

  5. Gateway 실행과 기록

    요청 검증 → action_started → 실제 행동 → action_finished. 결과와 수정된 상태가 다음 모델 턴으로 이어집니다.

  6. 제출 패치 확정

    finish_task가 현재 후보의 제출 조건을 확인합니다. 반환한 패치와 저장 artifact의 내용 해시도 같아야 합니다.

  7. dev 평가 또는 repair 전달

    dev는 manifest와 제출 patch를 별도 평가 공간으로 넘깁니다. repair는 공개 receipts와 patch를 반환하며 acceptance는 NOT_RUN입니다.

03 /

정확한 수정은 어떻게 성립하는가

모델은 교체할 텍스트와 수정 이유를 제안합니다. Gateway가 현재 관찰 근거와 실제 파일을 연결하고, 적용 후 전체 변경 범위를 검증합니다.

모델이 제출하는 여섯 필드

{
  "path": "허용된 기존 파일",
  "old_text": "관찰한 정확한 원문",
  "new_text": "교체할 내용",
  "occurrence": 1,
  "hypothesis": "예상하는 원인과 수정 메커니즘",
  "expected_behavior": "수정 후 기대하는 동작"
}

구조를 설명하는 예시입니다. 실제 수정 요청이나 실행 결과가 아닙니다. 가설과 기대 동작은 실행 전에는 검증되지 않은 주장입니다.

Gateway의 검증 순서

  1. Git 추적 파일이며 allowed / forbidden 경로 조건을 만족하는지 확인합니다.
  2. 현재 파일에 old_text의 지정한 occurrence가 존재하는지 확인합니다. occurrence="all"이면 관찰한 모든 정확한 일치를 한 번에 바꿉니다.
  3. 현재 파일 hash와 일치하는 관찰 구간이 교체 anchor를 연속적으로 덮는지 확인합니다.
  4. 새 파일 내용을 원자적으로 적용하고, 예상한 전체 candidate diff와 일치하는지 대조합니다.
  5. 누적 diff의 파일 수·변경 줄 수·경로 범위를 검사합니다. 적용 후 거절되면 이전 내용을 복원합니다.
관찰한 소스 ≠ 올바른 해석. 정확한 anchor를 확보했다는 것은 그 위치를 수정할 실행 근거가 있다는 뜻입니다. 원인 가설과 수정의 의미적 정확성은 별도 검증이 필요합니다.

기존 소스와 테스트 보존

기존 파일은 관찰한 정확한 문자열을 바꿉니다. edit_files는 허용된 새 파일도 만들 수 있습니다. 원래 테스트·fixture·공유 import는 보존하며, 새 테스트 모듈은 선언된 test root에서만 추가합니다. 과제의 경로·파일 수·diff·API 제한은 계속 적용됩니다.

전체 diff를 보는 이유

이번 교체 한 건만 작더라도 앞선 변경을 합친 결과가 과제 한도를 넘을 수 있습니다. 수정 범위와 검사 identity는 누적 후보 전체에 연결됩니다.

구현: _validate_replacement_intent / _apply_text_replacement · WorkspaceManager · 추가 테스트 보존 계약

도구와 제출 조건

모델에 임의 셸을 주지 않습니다. 각 응답은 읽기·검색 1~4개를 함께 요청하거나, 변경·실행·종료 도구 하나를 요청합니다. 현재 gate와 자원에 따라 허용 도구가 달라집니다.

왜 수정하면 다시 검사해야 할까?

설명용 상태 모형 · 실제 실행 없음
needs_mutation
현재 후보diff 없음
필수 검사 증거아직 없음

먼저 코드를 수정해 보세요. 수정 → 검사 PASS → 다시 수정 순서로 누르면 이전 PASS가 무효화됩니다.

이 모형의 행동 기록

  1. 변경이 없는 기준 상태에서 시작했습니다.
원래 case 근거: unverified → 제출 시 unverified_delivery
공통 조건: 비어 있지 않은 허용 범위 diff + 비무시 untracked 파일 없음 + 그 diff의 모든 필수 검사 PASS. 모형은 공개 검사 1개와 원래 case 상태를 단순화합니다. 자원·재현 acquisition·자동 replay·실제 파일·평가기는 실행하지 않습니다. 정책별 차이는 아래 설명을 함께 읽으세요.
read_file
search_files

공개 소스를 관찰합니다. 새 요청의 범위 읽기와 null bounds는 24,000자 페이지를 사용하며 별도 400줄 제한은 없습니다. 검색은 literal query와 루트 기준 glob입니다. 등록된 dependency/caller 소스는 읽기 전용 별도 scope입니다.

관찰 · 최대 4개
replace_text

이미 관찰한 기존 추적 파일의 정확한 문자열을 교체합니다. 현재 anchor·허용 경로·전체 diff를 검사하고, 거절되면 이전 내용을 복원합니다. 새 파일 생성이나 fuzzy matching은 지원하지 않습니다.

변경 · 1개
edit_files

최대 16개 경로를 한 행동으로 수정·생성하거나 undo_action_id로 이전 수정을 되돌립니다. 기존 파일은 정확한 관찰 anchor, 새 파일은 old_text=null과 전체 내용을 사용합니다. 한 묶음·undo마다 수정 슬롯 1회를 쓰며 과제 한도가 우선합니다. 이후 바뀐 대상 파일은 undo하지 않습니다.

변경 · 1개
run_check

과제에 등록된 공개 검사를 실행합니다. 현재 전체 diff에 묶인 필수 PASS만 제출 조건을 충족합니다. 수정하면 이전 후보의 결과는 과거 증거가 됩니다.

필수 검사 근거
run_tests
run_probe

활성화된 경우에만 기존 공개 pytest 선택 실행 또는 제한된 공개 진단 코드를 실행합니다. 검사 범위를 보완하는 관찰이며, 필수 검사 PASS를 대신하지 않습니다.

선택 기능
observe_original

제공되는 단계에서 첫 수정 전 원래 호출 경로의 전제를 조사합니다. 함수 진입과 특정 분기 실행을 구분합니다. 예상 관찰이 맞아도 수정 성공의 증거는 아닙니다.

선택적 원래 동작 관찰
search_history

public-v1을 명시적으로 활성화한 경우 같은 실행의 공개 기록을 찾습니다. 다른 과제의 경험을 검색하는 cross-run memory와는 다릅니다.

선택적 이력 복구
finish_task
stop_task

제출 조건을 만족한 후보를 고정하거나, 성공하지 못한 상태로 명시적으로 종료합니다. 준비된 제출은 전체 의미적 정확성의 인증이 아닙니다.

종료 · 1개

public-checks-v1

원래 재현·call-path 진단·관찰 교정은 참고 증거입니다. pending / refuted 상태 자체로 제출을 막지 않으며, 자동 원래 replay도 시작하지 않습니다. 현재 필수 공개 검사 PASS와 scoped diff가 제출 자격을 결정합니다.

reproduction-gated-v1

CLI 기본값입니다. 확보한 원래 case의 pending / refuted 상태와 알려진 target failure가 제출을 막을 수 있습니다. 오래된 invocation-bound case는 재검증 경로가 적용됩니다. 근거가 없거나 비교 불가능한 상태는 검증됨으로 바뀌지 않습니다.

도구 실행 성공과 테스트 성공도 다릅니다. status="succeeded" 안에 passed=false가 있을 수 있습니다. 검사를 실행하고 결과를 반환하는 데 성공했지만, 검사한 동작은 실패한 경우입니다.

기본 current policy는 해당 도구에 공개 turn_decision을 사용하고, thin은 간소화된 표현을 사용합니다. fresh replace_text·edit_files·stop_task·observe_original은 decision/plan/memory annotation을 생략합니다. agent policy와 verification policy는 서로 다른 설정입니다. 도구 구현 · 정확한 계약

무엇을 기억하고, 무엇을 복구하는가

모델이 보는 작업 상태와, 런타임이 남기는 복구 기록은 역할이 다릅니다. 모델의 노트는 해석이고, 실행 기록은 어떤 입력으로 무엇이 실행됐는지에 대한 증거입니다.

다음 모델 요청에 들어가는 것

공개 문제와 현재 실행 조건

요구사항, 허용 범위, 등록 도구, 제출 gate, 남은 호출·행동·시간.

실제로 관찰한 현재 소스

파일과 읽은 구간, 현재 diff와 변경 정보. 보지 않은 빈 구간을 채워 넣지 않습니다.

공개 행동과 검사 관찰

action/input/diff identity를 보존합니다. 수정 전 관찰과 현재 후보의 검사를 구분합니다.

제한된 실행 내 working notes

발견, 계획, 미해결 concern. 모델이 작성한 가설이며 판정·검증된 사실로 승격되지 않습니다.

컨텍스트 밖에 두는 것비공개 명세, hidden tests, reference patch, evaluator 내부 정보. 평가 출력도 코딩 에이전트에 피드백하지 않습니다. 원문 reasoning이나 reasoning summary는 기록하지 않습니다.

중단 이후 실행을 이어가는 근거

① Immutable envelope태스크·런타임·설정 등 실행 정체성을 고정합니다. 다른 코드/설정으로 같은 실행을 이어가지 않습니다.
② 외부 dev-run-v1 journal저장소 밖의 append-only, hash-chained JSONL과 content-addressed artifacts에 사건과 내용을 남깁니다.
③ action_id + input_hash완료한 수정·검사는 저장된 결과를 재사용합니다. 같은 ID에 다른 입력이면 거절하고, 중단된 변경은 증거를 대조합니다.
④ 정확한 조건으로 resumerepeat=1, 일치하는 envelope, run lock이 필요합니다. 이미 사용한 비용·자원·deadline을 보존합니다.
복구가 자동 재시도를 뜻하지는 않습니다.

provider dispatch 이후 사용량을 확정할 수 없으면 재시도하지 않습니다. evaluator도 durable completion receipt 이전의 중단에 대해 exactly-once 실행을 보장하지 않습니다.

실행 내 노트와 실행 간 메모리는 다릅니다.

cross-run memory retrieval은 비활성입니다. 과거 journal이 존재한다고 다음 문제의 모델 입력에 자동 주입되지는 않습니다.

01. 공개 검사가 PASS인데 acceptance는 FAIL일 수 있는 이유는?

공개 검사는 실행한 입력·경로만 확인합니다. 제출 자격과 독립 과제 평가는 다른 질문입니다. 현재 diff의 필수 PASS는 tools.py, 제출 후 acceptance는 verifier/core.py에서 다룹니다.

02. 왜 모델이 한 번 읽은 파일도 다시 읽어야 할 수 있을까?

수정 anchor에는 현재 파일 hash와 일치하고 정확한 구간을 덮는 관찰 근거가 필요합니다. 수정으로 source currency가 달라지거나 필요한 본문이 전달되지 않은 경우 재확인이 필요합니다. 단, 언제나 다시 읽도록 강제하는 것은 아닙니다.

03. 수정 직후 프로세스가 종료되면 같은 수정을 다시 실행할까?

먼저 action_id + input_hash와 pre/post-image, 전체 candidate diff를 확인합니다. 이미 적용된 변경이면 결과를 복원합니다. 파일 상태가 admission과 맞지 않으면 임의로 계속 진행하지 않습니다.

04. Journal과 working notes를 모두 메모리라고 부르면 무엇을 놓칠까?

Journal은 실행·복구 근거이고, working notes는 제한된 모델 해석입니다. 모델이 보는 공개 상태는 별도로 투영합니다. 둘이 존재해도 실행 간 유사 과제 검색이나 지속 학습을 구현했다는 뜻은 아닙니다.

05. 돈과 시간이 남았는데 replace_text가 사라질 수 있을까?

가능합니다. 현재 소스 근거가 없거나, 수정 후 필수 검사와 제출까지 이어질 모델 호출·행동 여력이 부족할 수 있습니다. 비용·시간·호출 수·도구 행동·수정 슬롯은 별도 제한입니다.

06. public-checks-v1과 thin은 같은 기능일까?

아닙니다. public-checks-v1은 제출에 어떤 검증 상태가 영향을 주는지를 정합니다. thin은 모델에게 제공하는 prompt와 annotation 표현을 간소화하는 agent policy입니다. 두 설정을 별도로 확인해야 합니다.
