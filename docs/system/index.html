PatchLoop는 제한된 자원 안에서 공개 소프트웨어 문제를 해결하는 단일 코딩 에이전트입니다. 실행 제어, 복구 기록, 샌드박스와 별도 평가기가 이 에이전트를 뒷받침합니다.

01 /

전체 구조

모델은 다음 행동을 선택하고, 런타임은 그 행동이 현재 소스·검사 결과·남은 자원에 맞는지 판단합니다. 아래 구성요소를 선택하면 책임과 실제 소스가 나타납니다.

INPUT / 공개 입력
↓ 공개 상태로 투영
↓ finish_task · 정확한 제출 diff 고정

화살표는 주요 실행 흐름을 나타냅니다. 컨텍스트·복구·자원 관리는 별도 에이전트가 아니라 루프 전반에 적용되는 런타임 기능입니다.

무엇을 제품으로 보는가

문제를 이해하고 올바른 코드를 제출하는 에이전트. 도구 사용 횟수나 노트 생성 자체는 목표가 아닙니다.

누가 무엇을 결정하는가

모델은 공개 도구로 행동을 제안합니다. 런타임이 계약을 검증하고 실제 부작용과 증거를 기록합니다.

성공은 어떻게 판단하는가

제출, 공개 검사, 과제 수용, 격리 안전성을 따로 봅니다. 제출 가능 상태만으로 정답이 보장되지는 않습니다.

02 /

한 번의 실행을 따라가기

일반적인 실행을 여섯 단계로 풀어 썼습니다. 탐색·수정·검사는 필요에 따라 반복됩니다. 이 단계들은 이해를 위한 구분이며 강제 계획 단계가 아닙니다.

별도 명령 repair-verify — 모델 호출 없이, 제출된 추가 pytest 케이스를 그대로 기준 코드와 수정 코드에 실행하여 비교합니다. 공개 검사도 기록하지만, 테스트 기대값이 요구사항과 맞는지 또는 패치가 수용 가능한지 판정하지는 않습니다. 지원하지 않는 분리는 UNSUPPORTED로 남습니다. 명령과 요청 형식
03 /

도구와 제출 조건

모델에 임의 셸을 주지 않습니다. 각 응답은 읽기·검색 1~4개를 함께 요청하거나, 변경·실행·종료 도구 하나를 요청합니다. 현재 gate와 자원에 따라 허용 도구가 달라집니다.

왜 수정하면 다시 검사해야 할까?

설명용 상태 모형 · 실제 실행 없음
needs_mutation
현재 후보diff 없음
필수 검사 증거아직 없음

먼저 코드를 수정해 보세요. 수정 → 검사 PASS → 다시 수정 순서로 누르면 이전 PASS가 무효화됩니다.

이 모형의 행동 기록

  1. 변경이 없는 기준 상태에서 시작했습니다.
필수 조건: 비어 있지 않은 추적 파일 diff + 허용 범위 준수 + 비무시 untracked 파일 없음 + 그 diff의 모든 필수 검사 PASS. 이 모형은 검사 1개와 diff 버전만 표현합니다. 실제 소스 수정·샌드박스·예산·평가는 실행하지 않습니다.
read_file
search_files

추적된 공개 소스를 관찰합니다. 읽기는 최대 400줄, 검색은 literal query와 루트 기준 glob을 사용합니다. 실제 전달된 현재 소스가 이후 수정의 근거가 됩니다.

관찰 · 최대 4개
replace_text

이미 관찰한 기존 추적 파일의 정확한 문자열을 교체합니다. 현재 anchor·허용 경로·전체 diff를 검사하고, 거절되면 이전 내용을 복원합니다. 새 파일 생성이나 fuzzy matching은 지원하지 않습니다.

변경 · 1개
run_check

과제에 등록된 공개 검사를 실행합니다. 현재 전체 diff에 묶인 필수 PASS만 제출 조건을 충족합니다. 수정하면 이전 후보의 결과는 과거 증거가 됩니다.

필수 검사 근거
run_tests
run_probe

활성화된 경우에만 기존 공개 pytest 선택 실행 또는 제한된 공개 진단 코드를 실행합니다. 검사 범위를 보완하는 관찰이며, 필수 검사 PASS를 대신하지 않습니다.

선택 기능
finish_task
stop_task

제출 조건을 만족한 후보를 고정하거나, 성공하지 못한 상태로 명시적으로 종료합니다. 준비된 제출은 전체 의미적 정확성의 인증이 아닙니다.

종료 · 1개

기본 agent policy는 제한된 공개 turn_decision을 행동에 동반합니다. 명시적 opt-in인 thin policy의 스키마는 다르지만 실행 gate는 공유합니다. 도구 구현 · 정확한 계약

04 /

무엇을 기억하고, 무엇을 복구하는가

모델이 보는 작업 상태와, 런타임이 남기는 복구 기록은 역할이 다릅니다. 모델의 노트는 해석이고, 실행 기록은 어떤 입력으로 무엇이 실행됐는지에 대한 증거입니다.

다음 모델 요청에 들어가는 것

공개 문제와 현재 실행 조건

요구사항, 허용 범위, 등록 도구, 제출 gate, 남은 호출·행동·시간.

실제로 관찰한 현재 소스

파일과 읽은 구간, 현재 diff와 변경 정보. 보지 않은 빈 구간을 채워 넣지 않습니다.

공개 행동과 검사 관찰

action/input/diff identity를 보존합니다. 수정 전 관찰과 현재 후보의 검사를 구분합니다.

제한된 실행 내 working notes

발견, 계획, 미해결 concern. 모델이 작성한 가설이며 판정·검증된 사실로 승격되지 않습니다.

컨텍스트 밖에 두는 것비공개 명세, hidden tests, reference patch, evaluator 내부 정보. 평가 출력도 코딩 에이전트에 피드백하지 않습니다. 원문 reasoning이나 reasoning summary는 기록하지 않습니다.

중단 이후 실행을 이어가는 근거

① Immutable envelope태스크·런타임·설정 등 실행 정체성을 고정합니다. 다른 코드/설정으로 같은 실행을 이어가지 않습니다.
② 외부 dev-run-v1 journal저장소 밖의 append-only, hash-chained JSONL과 content-addressed artifacts에 사건과 내용을 남깁니다.
③ action_id + input_hash완료한 수정·검사는 저장된 결과를 재사용합니다. 같은 ID에 다른 입력이면 거절하고, 중단된 변경은 증거를 대조합니다.
④ 정확한 조건으로 resumerepeat=1, 일치하는 envelope, run lock이 필요합니다. 이미 사용한 비용·자원·deadline을 보존합니다.
복구가 자동 재시도를 뜻하지는 않습니다.

provider dispatch 이후 사용량을 확정할 수 없으면 재시도하지 않습니다. evaluator도 durable completion receipt 이전의 중단에 대해 exactly-once 실행을 보장하지 않습니다.

실행 내 노트와 실행 간 메모리는 다릅니다.

cross-run memory retrieval은 비활성입니다. 과거 journal이 존재한다고 다음 문제의 모델 입력에 자동 주입되지는 않습니다.

선택된 segmented-v1에서는 이전에 관찰한 소스의 24,000자 보존 설정과 별도의 60,000-token segmented 한도를 구분합니다. 큰 이력 한도 안에서도 결과 전달 시 오래된 이력이 정리될 수 있습니다. 컨텍스트·복구 계약

자원과 실행 설정

자원은 모델이 다음 행동을 선택하기 전에 고려됩니다. 종료에 필요한 경로를 남겨 두고, provider dispatch 직전에 실제 입력을 count하여 비용을 허용합니다.

40model calls
100tool actions
4accepted edits
1,800 s하나의 전체 deadline

행동과 호출을 따로 계산

자동 required-check recheck는 모델 호출 0회, 도구 행동 1회입니다. 최소 완료 경로와 보호된 여유를 구분합니다.

예약 비용과 청구를 구분

입력·출력 비용을 보수적으로 예약합니다. 허용 잔액에 따라 출력 한도를 낮출 수 있습니다. 미확정 사용량을 0으로 처리하지 않습니다.

불확실하면 반복 전체 중단

SDK retry는 0입니다. count·transport·billing·cleanup 불확실성은 남은 반복의 새 실행도 중단시킵니다.

07 /

결과를 읽는 네 가지 축

공개 검사 PASS는 검사한 사례에 대한 관찰입니다. 제출과 과제 수용, 안전성, 비용 상태를 한 개의 성공 표시로 합치지 않습니다.

구현됨

코드·계약이 존재합니다. 실제 provider나 Docker 경로를 실행했다는 뜻은 아닙니다.

로컬 검증됨

해당 테스트·mock 조건에서 동작을 확인했습니다. mock safety는 NOT_RUN입니다.

실제로 실행됨

특정 태스크·설정·예산에서 관측한 결과입니다. fresh solve와 replay를 구분합니다.

일반 성능 주장

현재 모든 실행은 official=false, claim-ineligible입니다. 개발 결과를 일반 정확도로 읽지 않습니다.

이 상태들은 동시에 존재할 수 있습니다

  • 패치 제출 성공 + 공개 검사 PASS + 과제 acceptance FAIL
  • mock acceptance PASS + Docker safety NOT_RUN
  • 부분 실행 완료 + 나머지 NOT_RUN
  • 비용 예약 존재 + 실제 billing 불확실

모두 상태 구분을 보여 주는 예시이며, 특정 실행의 결과를 재현한 화면이 아닙니다.

현재 범위

소스 탐색, 제한된 수정, 등록 검사, 선택적 공개 진단, 자원 제어, 정확한 실행 복구, 제출 후 격리 평가가 구현 범위입니다.

cross-run memory, validation/held-out tuning, claim execution은 비활성입니다. 과거 Rapid 실행기와 candidate/qualification 흐름은 현재 런타임에 없습니다.
